# 규칙 기반 한국어 정보 추출과 감성 분석

자연어 처리(NLP, Natural Language Processing)는 사람이 쓰는 언어를 컴퓨터가 읽고 분석할 수 있도록 다루는 분야다. 문장에서 연락처를 찾거나 리뷰가 긍정인지 부정인지 판단하는 일이 여기에 해당한다.

고객 문의와 리뷰에서 이메일·전화번호·날짜·금액·URL을 찾아 표준 형식으로 변환하고, KNU 감성사전과 부정·강조 규칙으로 문장의 감성을 판정한다. 출력은 추출값과 감성 점수의 근거를 담은 JSON이다.

## 빠른 실행

Python 3.10 이상에서 저장소 루트를 열고 실행한다. 첫 명령은 공식 사전과 평가 데이터를 내려받는다.

```powershell
python setup_data.py
python -X utf8 main.py --text "정말 좋지 않다. 전화 (02) 123-4567"
```

이 예시는 전화번호를 `02-123-4567`로 정규화하고 감성 점수 `-3`을 반환한다.

## 1. 다섯 가지 정보 추출 패턴

`nlp/extract.py`의 `PATTERNS`에 이메일·전화·날짜·금액·URL 정규식을 등록한다. Python 표준 라이브러리 `re`를 사용하며, 유형별 대표 변형과 출력 형식은 다음과 같다.

| 유형 | 지원 예 | 정규화 |
| --- | --- | --- |
| 이메일 | `user@example.com`, `user.name@sub.example.co.kr`, `user+orders@example.org` | 도메인을 소문자로 바꾸고 로컬 파트는 원문 유지 |
| 전화 | `010-1234-5678`, `(02) 123-4567`, `031 1234 5678`, `01012345678`, `+82 10-1234-5678`, `공일공-일이삼사-오육칠팔` | 국내 하이픈 형식으로 통일 |
| 날짜 | `2024년 1월 15일`, `2024/01/15`, `2024-01-15`, `2024.1.15` | `YYYY-MM-DD`, 달력에 없는 날짜 제외 |
| 금액 | `10,000원`, `1억 2천만원`, `$100`, `₩2,500` | 정수 `amount`와 `currency`를 함께 반환 |
| URL | `http://example.com`, `https://example.com/path?q=1`, `www.example.com` | 스킴과 호스트를 소문자로 바꾸고 `www.`로 시작하면 `https://` 추가 |

평가 케이스는 유형별로 이메일 `E01–E12`, 전화 `E13–E24`, 날짜 `E25–E36`, 금액 `E37–E48`, URL `E49–E60`에 있다. 각 행에서 입력과 정규화된 정답을 확인할 수 있다. [전체 평가 케이스](data/extraction.jsonl)

회귀 테스트는 이메일의 점·별칭, 전화의 공백·괄호·국가번호·한글 숫자, 날짜 구분자와 윤일, 원화 단위와 달러, URL 스킴과 쿼리를 검증한다. 날짜와 금액의 잘못된 표기, URL 경로의 중복 추출도 확인한다. [정규식 회귀 테스트](tests/test_regression.py)

## 2. 부정어와 적용 범위

`안 좋다`처럼 감성 표현 바로 앞의 `안`·`못`을 발견하거나, `좋지 않다`처럼 `-지` 계열 어미 바로 뒤에 `않다`·`못하다` 계열 활용형이 오면 점수의 부호를 뒤집는다. `좋지, 않다`는 쉼표가 두 표현 사이에 있어 부정 규칙이 연결되지 않는다. `정말 안 좋다`의 `안`은 `좋다`의 점수만 반전한다.

부정 표현은 `nlp/sentiment.py`에서 앞말 목록(`PRE_NEGATION`)과 뒷말 패턴(`POST_NEGATION`)으로 관리한다. 새 표현을 검토할 때는 토큰 위치와 어미 조건을 먼저 확인하고, 일반 어절에서 오탐이 없는지 회귀 테스트로 확인한다. 여러 도메인이 서로 다른 부정 목록을 필요로 할 경우 앞말 목록을 별도 데이터로 분리할 수 있다. 뒷말의 활용형과 적용 범위는 토큰 구조를 검증하는 코드에 둔다.

## 3. 강조어와 가중치

`매우`·`정말`은 ×1.5, `완전`·`엄청`은 ×2, `조금`·`약간`은 ×0.5다. 감성 표현 바로 앞의 강조어 하나를 적용한다. 바로 앞이 `안`이나 `못`이면 그 한 어절을 건너뛰어 강조어를 찾는다. `완전 정말 좋다`에서는 가장 가까운 `정말`의 ×1.5만 적용되며, `정말 안 좋다`는 `(+2) × (-1) × 1.5 = -3`이다.

| 범주 | 표현 | 가중치와 설계 이유 |
| --- | --- | --- |
| 약화 | 조금, 약간 | ×0.5로 강도를 절반으로 줄인다. |
| 일반 강조 | 매우, 정말, 아주, 너무, 무척, 진짜 | ×1.5로 한 단계 강화한다. |
| 강한 강조 | 완전, 엄청, 굉장히 | ×2로 강도를 두 배로 높인다. |
| 기본 | 인접한 강조어가 없는 경우 | ×1로 원래 점수를 유지한다. |

이 배수는 사람이 정한 규칙이다. 강조어나 약화어만으로 부호가 바뀌지는 않는다. 회귀 테스트에서 `조금 좋다`, `완전 정말 좋다`, `정말 안 좋다`를 비교한다.

## 4. 추출 결과 정규화

전화번호는 하이픈 문자열 `02-123-4567`, 날짜는 ISO 8601 문자열 `2024-03-15`, 금액은 정수 `amount: 5000`과 통화 코드 `KRW`로 정규화한다. 각 유형의 결과는 입력 순서대로 배열에 담는다.

아래 명령을 실행하면 세 정규화 결과를 같은 응답의 `information`에서 확인할 수 있다.

```powershell
python -X utf8 main.py --text "정말 좋지 않다. 전화 (02) 123-4567, 접수 2024년 3월 15일, 비용 5,000원"
```

```json
{
  "email": [],
  "phone": ["02-123-4567"],
  "date": ["2024-03-15"],
  "money": [{"amount": 5000, "currency": "KRW"}],
  "url": []
}
```

| 유형 | 반환 형식과 코드 |
| --- | --- |
| 전화번호 | `"-".join((area, match["middle"], match["last"]))`로 하이픈 문자열을 반환한다. |
| 날짜 | `date(…).isoformat()`으로 달력 검증을 마친 ISO 8601 날짜 문자열을 반환한다. |
| 금액 | `{"amount": parse_won(match["won"]), "currency": "KRW"}`처럼 정수 금액과 통화 코드를 반환한다. 기호 표기는 `int(...)`로 변환한다. |

[정규화 함수](nlp/extract.py#L82)와 [통합 출력 테스트](tests/test_regression.py#L112)에서 같은 반환 형식을 확인할 수 있다.

| 입력 | 정규화 결과 |
| --- | --- |
| `User@SUB.Example.com` | `User@sub.example.com` |
| `(02) 123-4567` | `02-123-4567` |
| `+82 10-1234-5678` | `010-1234-5678` |
| `공일공-일이삼사-오육칠팔` | `010-1234-5678` |
| `2024년 3월 15일` | `2024-03-15` |
| `5,000원` | `{"amount": 5000, "currency": "KRW"}` |
| `www.example.com/path` | `https://www.example.com/path` |

국가번호 표기는 한국의 `+82`를 지원하며 국내 번호에 필요한 앞자리 `0`을 복원한다. 한글 숫자는 하이픈으로 자릿수 묶음을 구분하고 `공`과 `영`을 모두 `0`으로 바꾼다. 다른 국가의 번호 형식과 하이픈 없이 적은 한글 숫자는 현재 범위 밖이다.

## 5. 평가 방법과 성능

`evaluate.py`로 정보 추출과 감성 분석을 재현할 수 있다. 결과는 기본적으로 콘솔에 표시되며, PowerShell에서는 다음처럼 저장소 루트의 `evaluation.txt`에 UTF-8로 저장할 수 있다.

```powershell
python -X utf8 evaluate.py --errors 30 | Out-File -Encoding utf8 evaluation.txt
```

정보 추출은 `data/extraction.jsonl`에 직접 작성한 60문장으로 평가했다. 유형별 12문장에 대해 문장과 유형마다 정규화된 값의 **출현 횟수**를 비교한다. 정답과 일치하면 TP, 정답에 없는 출력은 FP, 빠진 정답은 FN이다. 같은 값이 반복되면 반복 횟수만큼 집계한다. 정밀도는 `TP / (TP + FP)`, 재현율은 `TP / (TP + FN)`이다.

| 유형 | TP | FP | FN | 정밀도 | 재현율 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 이메일 | 10 | 0 | 2 | 100.0% | 83.3% |
| 전화 | 10 | 0 | 1 | 100.0% | 90.9% |
| 날짜 | 9 | 0 | 2 | 100.0% | 81.8% |
| 금액 | 9 | 0 | 2 | 100.0% | 81.8% |
| URL | 9 | 1 | 2 | 90.0% | 81.8% |

| 유형 | 정밀도 95% Wilson 구간 | 재현율 95% Wilson 구간 |
| --- | ---: | ---: |
| 이메일 | 72.2–100.0% | 55.2–95.3% |
| 전화 | 72.2–100.0% | 62.3–98.4% |
| 날짜 | 70.1–100.0% | 52.3–94.9% |
| 금액 | 70.1–100.0% | 52.3–94.9% |
| URL | 59.6–98.2% | 52.3–94.9% |

정밀도 구간에는 `TP + FP`, 재현율 구간에는 `TP + FN`을 분모로 썼다. 정보 추출 문장은 직접 구성한 소표본이므로 이 구간은 관측 건수의 불확실성을 보여 주는 참고값이다. 실제 고객 문의의 모집단 성능을 추정한 값은 아니다.

감성 분석은 두 설정에서 같은 토큰화와 사전으로 NSMC 공식 테스트셋을 평가했다. 원본 50,000건 중 본문이 비어 있는 3건을 제외해 긍정 25,171건과 부정 24,826건을 사용했다. 점수가 0인 중립 예측은 오답으로 집계했다. Macro F1은 긍정과 부정 F1의 산술평균이다.

| 설정 | 정답 수 | 정확도 | 긍정 F1 | 부정 F1 | Macro F1 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 사전만 | 19,492/49,997 | 39.0% | 0.557 | 0.460 | 0.509 |
| 사전 + 부정·강조 규칙 | 19,725/49,997 | 39.5% | 0.562 | 0.464 | 0.513 |

`정말 좋지 않다`는 사전만 사용하면 `+2`이고, 부정어와 강조어를 함께 적용하면 `-3`이다. 이전 단일 어절 버전의 정확도는 37.3%였고, 영화 리뷰 어휘와 구절을 추가한 뒤 동일한 평가 방식에서 39.5%를 기록했다.

`python evaluate.py --binary`로 긍정·부정 중 하나를 출력하는 조건도 평가했다.

| 이진 평가 설정 | 정확도 | Macro F1 |
| --- | ---: | ---: |
| 전부 긍정으로 예측 | 50.3% | 0.335 |
| 이전 단일 어절 버전 + 규칙 | 60.4% | 0.569 |
| 현재 사전만 | 60.9% | 0.577 |
| 현재 사전 + 규칙 | 61.2% | 0.580 |

규칙 적용 정확도의 95% Wilson 구간은 기본 모드 39.0–39.9%, 이진 모드 60.8–61.6%다. 두 모드는 0점 처리 정책이 다르므로 같은 판정 기준의 성능 변화는 표 안에서 비교한다.

이진 모드에서 0점 리뷰 23,530건에 긍정을 부여했다. 같은 이진 조건에서 어휘와 구절을 확장한 순효과는 60.4%에서 61.2%로의 변화다. 이전에 오류를 확인한 NSMC 테스트셋을 다시 사용한 결과이며, 별도 리뷰 집합에서도 같은 성능이 나오는지는 확인하지 않았다.

## 6. 설치 및 실행

Python 3.10 이상이 필요하다. 분석 실행과 일반 회귀 테스트에는 Python 표준 라이브러리만 사용한다. 코드 커버리지를 측정할 때만 `coverage==7.10.7`이 필요하며 설치 명령은 [16번](#16-회귀-테스트와-ci)에 있다. 첫 실행 전에 공식 데이터를 내려받을 때 인터넷 연결이 필요하다. 저장소 루트에서 실행한다.

Conda로 실행 환경을 만들려면 다음 명령으로 `environment.yml`을 사용한다. Python 3.10 이상이 이미 설치되어 있으면 바로 아래 데이터 준비 단계부터 진행할 수 있다.

```powershell
conda env create -f environment.yml
conda activate rule-based-nlp
```

```powershell
python setup_data.py
python -X utf8 main.py --text "정말 좋지 않다. 문의 help@example.com, 전화 (02) 123-4567, 접수 2024년 3월 15일, 비용 5,000원, 링크 https://example.com/help"
python -X utf8 evaluate.py
```

`setup_data.py`는 고정 버전의 `data/SentiWord_info.json`과 `data/ratings_test.txt`를 내려받고 SHA-256으로 검증한다. `main.py`에는 KNU 사전과 저장소의 `data/domain_lexicon.csv`가 필요하다. `evaluate.py`에는 이 두 사전과 `data/extraction.jsonl`, NSMC의 `data/ratings_test.txt`가 필요하다.

- `main.py --baseline`은 부정·강조 가중치를 끄고 사전 점수만 합산한다.
- `evaluate.py --errors 30`은 감성 오분류 예시를 최대 30건 출력한다. 기본값은 20이며, `--errors 0`은 해당 예시를 생략한다.
- `--binary`는 두 스크립트에서 쓸 수 있으며, 0점일 때 긍정 라벨을 부여한다.

## 7. 모듈을 분리한 이유

`main.py`는 명령줄 입력과 JSON 출력만 맡고, `nlp/extract.py`와 `nlp/sentiment.py`는 문자열을 받아 결과를 반환한다. 그래서 다른 프로그램이 CLI를 거치지 않고 각 함수를 가져다 쓸 수 있고, 회귀 테스트도 정규화와 감성 규칙을 따로 검증할 수 있다. `evaluate.py`는 같은 함수를 호출해 정답과 비교하므로 평가 전용 코드가 실행 동작을 바꾸지 않는다. `setup_data.py`가 다운로드를 담당하므로 파일을 준비한 후에는 분석을 오프라인으로 실행할 수 있다. 정규식이나 사전을 바꿀 때 CLI와 지표 집계 코드를 따로 수정할 필요가 없다.

정보 추출은 표기 형식과 정규화가 바뀔 때 수정하고, 감성 분석은 어휘와 점수 규칙이 바뀔 때 수정한다. 변경 이유가 달라 두 모듈을 독립시켰다. `ExtractionTests`는 정규화된 값과 중복 검사를, `SentimentTests`는 점수와 규칙 적용 범위를 직접 검증한다. `CLITests`는 이 결과들이 같은 입력에서 JSON으로 합쳐지는지 검증한다.

| 파일 | 역할 |
| --- | --- |
| `main.py` | 정보 추출과 감성 분석을 함께 실행하는 CLI |
| `nlp/extract.py` | Python `re`로 탐지하고 결과 정규화 |
| `nlp/sentiment.py` | 한국어 어절 토큰화, 감성 점수 계산, 부정·강조 처리 |
| `evaluate.py` | 정밀도, 재현율, 정확도, F1 및 실패 사례 출력 |
| `data/extraction.jsonl` | 직접 작성한 문장 60개. 유형별 12문장과 정규화된 정답 |
| `setup_data.py` | 공식 KNU 사전과 NSMC 테스트셋을 내려받고 SHA-256 확인 |
| `data/ratings_test.txt` | 공식 NSMC 테스트 리뷰. 설치 단계에서 다운로드 |
| `data/SentiWord_info.json` | 공식 KNU 한국어 감성사전. 설치 단계에서 다운로드 |

## 8. 패턴과 감성 사전 확장 절차

`extract(text: str)`는 `{"email": [...], "phone": [...], "date": [...], "money": [...], "url": [...]}` 형식의 딕셔너리를 반환한다. 각 배열에는 해당 유형의 정규화 값이 들어간다. `normalize(kind, match)`는 `re.Match` 하나를 받아 정규화 값 하나를 반환한다. 값이 유효하지 않으면 `ValueError`로 해당 매칭을 제외한다.

새 유형으로 접수 번호를 추가한다면 다음 순서로 작업한다.

1. `nlp/extract.py`에 `TICKET = re.compile(r"(?<![A-Za-z0-9])(?P<prefix>[A-Za-z]{3})-(?P<number>[0-9]{5})(?![0-9])")`을 추가하고 `PATTERNS["ticket"] = TICKET`으로 등록한다.
2. `normalize`의 URL 처리 앞에서 `ticket` 분기를 만들고 `prefix`를 대문자로 바꾼 뒤 `number`와 결합한다. `extract`의 우선순위 순회에 `ticket`을 추가한다. URL 경로에도 접수 번호가 들어갈 수 있으므로 URL보다 뒤에 둔다.
3. 기존 평가 행의 `expected`에 `"ticket": []`를 추가하고 새 유형의 정답 행과 회귀 테스트를 넣는다. 정상 표기, 허용하지 않는 자릿수, URL 내부 중복을 각각 검증한다.

`data/extraction.jsonl`에 추가할 한 줄의 예시는 다음과 같다. `focus`는 대표 평가 유형이며, `expected`는 문장 전체에서 추출할 정규화 값이다.

```json
{"id":"E61","focus":"ticket","text":"접수 번호 abc-12345","expected":{"email":[],"phone":[],"date":[],"money":[],"url":[],"ticket":["ABC-12345"]}}
```

감성 표현은 `data/domain_lexicon.csv`의 `term,score` 형식으로 추가한다. 예를 들어 `재발송 지연,-2`를 한 줄 추가하고 그 표현만 입력했을 때 `-2`가 나오는지 테스트한다. 공백이 있는 표현은 입력에서 여러 어절이 연속으로 일치해야 한다. 같은 키를 KNU에도 찾을 수 있으면 도메인 CSV 점수가 우선한다. 데이터 파일 변경 후 `python -m unittest discover -s tests -v`와 `python -X utf8 evaluate.py`를 실행한다.

도메인 사전과 평가 데이터는 Git에서 함께 관리한다. KNU·NSMC 원본을 갱신할 때는 `setup_data.py`의 원본 커밋 URL과 SHA-256을 함께 바꾸고 평가표와 오분류 예시를 다시 생성한다.

## 9. 정규식 문법과 설계

`[0-9]{3,4}`처럼 수량자로 자릿수를 제한한다. `(?:…)`는 캡처 없이 선택지를 묶고, `(?P<year>…)`는 후처리에 필요한 값을 이름으로 캡처한다. 날짜의 `(?P=sep)`는 연·월·일 사이의 구분자가 같은지 확인한다. `(?<![0-9])` 같은 전후방 검사는 긴 번호 일부를 잘못 추출하는 일을 줄인다. URL과 이메일 내부의 문자열은 다른 유형의 값으로 중복 집계하지 않는다.

| 입력 | 정규식에서 잡는 값 | 정규화 |
| --- | --- | --- |
| `User@SUB.Example.com` | `local=User`, `domain=SUB.Example.com` | `User@sub.example.com` |
| `+82 10-1234-5678` | `international_area=10`, `middle=1234`, `last=5678` | `010-1234-5678` |
| `2024/2/29` | `year=2024`, `sep=/`, `nm=2`, `nd=29` | 달력 검증 후 `2024-02-29` |
| `1억 2천만원` | `won=1억 2천만` | `{"amount": 120000000, "currency": "KRW"}` |
| `www.example.com/path.` | 전체 주소와 끝의 마침표 | `https://www.example.com/path` |

## 10. 감성 점수 계산과 임계값

한글·영숫자 어절과 문장부호로 입력을 나눈다. 여러 어절의 사전 표현이 겹치면 가장 긴 표현을 한 번만 계산하고, 그 외에는 어절에 맞는 가장 긴 감성 어간을 찾는다. 각 표현의 점수는 `기본 점수 × (-1)^부정 횟수 × 가중치`이며, 최종 점수는 이 값들의 합이다.

| 기본 점수 | -2 | -1 | +1 | +2 |
| --- | ---: | ---: | ---: | ---: |
| 실제 조회 키 개수 | 4,960 | 5,241 | 2,511 | 2,751 |

0은 긍정과 부정의 순점수가 균형을 이루는 기준이므로, 기본 모드에서는 양수를 긍정, 음수를 부정, 0을 중립으로 분류한다. 이 기준은 NSMC에서 학습한 임계값이 아니다. `hits`에는 매칭된 표현과 기본 점수, 부정 횟수, 가중치, 최종 점수를 담는다.

예를 들어 `정말 좋지 않다`에서 `좋`의 `+2`가 부정어로 `-2`가 되고 강조 배수 `1.5`를 곱해 `-3`이 된다. 점수는 합계를 그대로 쓰므로 문장 길이에 따라 범위가 달라지며, 확률이나 고정 범위의 점수로 해석하지 않는다.

군산대학교 Data Intelligence Lab의 KNU 한국어 감성사전에서 극성이 0이 아닌 한글 단어와 구절을 사용한다. 어간은 표제어와 원본 어근 사이의 차이가 코드의 활용 규칙에 맞을 때 등록한다. 도메인 항목까지 합쳐 단어·어간 조회 키 7,891개와 여러 어절로 된 표현 7,572개를 사용한다. [KNU 한국어 감성사전 원본](https://github.com/park1200656/KnuSentiLex/tree/c95a8a9bcb78ef92e3f8ddd277abaf31451d9f23)

감성 분석 평가는 NSMC 공식 테스트 분할을 사용한다. 긍정 레이블은 1, 부정 레이블은 0이다. [NSMC 데이터와 설명](https://github.com/e9t/nsmc/tree/eafdd77e310f399a4d0083a58ade40b55a5a308d)

## 11. 정밀도와 재현율의 균형

정밀도는 찾은 값이 얼마나 정확한지, 재현율은 정답을 얼마나 놓치지 않았는지를 나타낸다. 예를 들어 `배송일 20241109`와 `주문번호 20241109`가 한 건씩 있을 때, 구분자가 있는 날짜만 허용하면 배송일을 놓친다. 8자리 숫자를 모두 날짜로 처리하면 배송일을 찾지만 주문번호도 날짜로 오인한다. 이런 형식을 추가할 때는 숫자 길이와 함께 앞에 나오는 `배송일` 같은 단서를 검증해야 한다.

예를 들어 연락처가 자동 등록되는 업무라면 오등록을 줄이기 위해 정밀도 99% 같은 목표를 먼저 정할 수 있다. 사람이 결과를 검토하는 검색 업무라면 누락을 줄이기 위해 재현율 90% 같은 목표를 둘 수 있다. 이 숫자는 운영 기준을 고르는 예시이며 실제 목표는 현장 데이터와 오류 비용으로 결정한다.

## 12. 이중부정과 적용 한계

`좋지 않지 않다`에서는 `좋지` 뒤에 `않지`와 `않다`가 연달아 나온다. 이 경우 부정 2회로 처리해 `+2 × (-1)^2 = +2`가 된다. 중간에 다른 어절이나 문장부호가 끼면 두 번째 부정까지 연결하지 않는다. `좋지 않은 건 아니다`처럼 멀리 떨어진 부정은 이 규칙의 범위 밖이라, 전체 의미와 반대로 분류될 수 있다.

조사가 붙은 `좋지는 않지는 않아요`도 같은 조건으로 `+2`가 된다. 두 형태 모두 회귀 테스트에 포함한다.

## 14. 유지보수와 도메인 전이

정규식과 사전은 판정 근거를 추적하기 쉽지만, 한 규칙을 넓히면 기존 문장에서도 결과가 바뀔 수 있다. 예를 들어 새 통화 단위를 추가할 때는 정상 금액, 일반 숫자, URL에 포함된 숫자를 다시 검증한다. 업종을 바꾸면 대상 표현과 극성이 달라질 수 있으므로 도메인 CSV를 먼저 검토한다. 변경 커밋에는 추가한 규칙이나 표현이 드러나는 제목을 사용하고, 평가표가 달라진 경우 README 수치와 오류 사례를 함께 갱신한다.

실제로 한글 전화번호를 추가할 때는 숫자 변환, 국가번호, 잘못된 자릿수의 테스트를 함께 수정했다. 기존 60개 문장을 다시 평가해 전화 재현율이 81.8%에서 90.9%로 올랐고 거짓 양성은 0건임을 확인했다. 이처럼 변경 비용에는 규칙 수정 외에 정상·실패 케이스 보강과 전체 평가 재실행이 포함된다.

## 15. 규칙 기반과 통계 기반 비교

정규식은 형식이 정해진 이메일·전화번호를 추출하거나 날짜를 정규화할 때 적합하다. 사전 규칙은 분석 근거를 바로 확인해야 하거나 레이블이 부족한 초기 고객 문의 분류에 적합하다. 반면 레이블이 있는 리뷰가 충분하면 TF-IDF로 문서를 벡터화해 코사인 유사도로 유사한 리뷰를 찾거나, 그 벡터로 분류기를 학습해 사람이 일일이 정의하지 않은 단어의 단서도 활용할 수 있다. 이 프로젝트의 성능표는 동일한 NSMC 데이터에서 사전만 사용한 설정과 부정·강조 규칙을 함께 사용한 설정을 비교한다.

| 데이터 조건 | 먼저 적용할 방법 |
| --- | --- |
| 규모와 관계없이 표기 규칙이 있는 필드 | 정규식으로 추출하고 정규화한다. |
| 문장 레이블이 거의 없고 판정 근거가 필요한 경우 | 사전과 부정·강조 규칙으로 기준선을 만든다. |
| 레이블 없이 문서 수가 늘고 유사 문서를 검색하는 경우 | TF-IDF와 코사인 유사도를 적용한다. |
| 클래스별 레이블이 충분해 학습·검증 데이터를 나눌 수 있는 경우 | TF-IDF 분류기를 학습해 검증 데이터에서 규칙 기반과 비교한다. |

## 16. 회귀 테스트와 CI

`tests/test_regression.py`는 표준 라이브러리 `unittest`로 기대 출력과 실제 출력을 비교한다. 실행 방법은 다음과 같다.

```powershell
python setup_data.py
python -m unittest discover -s tests -v
```

| 검증 대상 | 자동으로 확인하는 동작 |
| --- | --- |
| 정보 추출 | 유형별 대표 변형 3개, 정규화, 존재하지 않는 날짜·잘못된 쉼표 형식 거절, URL 내부 중복 방지 |

| 평가 | 정보 추출 데이터의 TP·FP·FN 예시와 감성 정확도·F1 계산 |

GitHub Actions는 push와 pull request에서 Python 3.10을 준비하고 공식 데이터를 내려받은 후, 회귀 테스트와 코드 커버리지 측정을 실행한다. 실패한 테스트가 있으면 CI도 실패한다. [워크플로우 설정](.github/workflows/tests.yml)

코드 커버리지는 `nlp`와 `evaluate.py`의 실행문과 분기를 대상으로 한다. 회귀 테스트 8개를 실행한 결과 이 범위의 합산 커버리지는 97%였다. `main.py`는 별도 프로세스로 실행하는 통합 테스트로 검증한다. 로컬에서 CI와 같은 범위를 측정하려면 다음 명령을 사용한다.

```powershell
python -m pip install coverage==7.10.7
python -m coverage run --branch --source=nlp,evaluate -m unittest discover -s tests -v
python -m coverage report -m
python -m coverage xml -o coverage.xml
```

CI 실행 요약에 파일별 커버리지와 미실행 위치가 표시된다. 실행 페이지의 `coverage-report`에서 `coverage.txt`와 `coverage.xml`도 내려받을 수 있다. 패턴이나 사전을 변경할 때는 실패 사례를 회귀 테스트에 추가하고, 변경 후 테스트와 데이터셋 평가를 각각 실행한다. [Actions 실행 목록](https://github.com/js910/rule-based-nlp/actions)

## 17. 복합 감성과 중립 처리

서로 다른 절의 감성도 같은 문장 점수에 더한다. `좋다. 나쁘다.`는 `+2 - 2 = 0`으로 중립이며, `정말 좋다. 나쁘다.`는 `+3 - 2 = +1`로 긍정이다. 어느 절도 자동으로 우선하지 않으며, 단어를 하나도 찾지 못한 문장도 점수는 0이다. `hits`가 비어 있는지 보면 미탐과 점수 상쇄를 구별할 수 있다. `--binary`는 두 경우의 0점을 모두 긍정으로 출력한다.

출력의 `information`에는 다섯 유형의 배열이 있고, 금액 원소는 `amount` 정수와 `currency` 문자열을 가진다. `sentiment`에는 `label` 문자열, `score` 숫자, `tokens` 문자열 배열, `hits` 객체 배열이 있다. `좋다. 나쁘다.`의 감성 출력은 다음과 같다.

```json
{
  "label": "중립",
  "score": 0.0,
  "tokens": ["좋다", ".", "나쁘다", "."],
  "hits": [
    {"token": "좋다", "term": "좋다", "base": 2, "negations": 0, "weight": 1.0, "score": 2.0},
    {"token": "나쁘다", "term": "나쁘다", "base": -2, "negations": 0, "weight": 1.0, "score": -2.0}
  ]
}
```
