# 규칙 기반 한국어 정보 추출과 감성 분석

## 1. 프로젝트 개요

고객 문의와 리뷰에서 **이메일·전화번호·날짜·금액·URL을 추출하고 정규화**하며, **감성사전과 부정·강조 규칙으로 긍정·부정을 판단**하는 Python 프로그램이다.

```text
입력 문장
  ├─ 정보 추출: 정규표현식으로 탐지 → 유효성 확인 → 형식 통일
  └─ 감성 분석: 토큰화 → 사전 조회 → 부정·강조 적용 → 점수 합산
                                  ↓
                      추출 결과와 감성 계산 과정 출력
```

정보 추출과 감성 분석은 같은 입력을 각각 처리한다. 모델을 학습하는 과정은 없으며, 사람이 정의한 패턴·사전·규칙을 사용한다. 점수와 계산 근거를 확인할 수 있지만 문맥이나 반어까지 이해하지는 못한다.

| 파일 | 역할 |
| --- | --- |
| [main.py](main.py) | 명령줄 입력, 통합 실행, 텍스트/JSON 출력 |
| [nlp/extract.py](nlp/extract.py) | 다섯 정보 유형의 정규식, 유효성 검사, 정규화 |
| [nlp/sentiment.py](nlp/sentiment.py) | 사전 준비, 토큰화, 감성 표현 조회, 규칙 적용 |
| [setup_data.py](setup_data.py) | 고정 버전의 외부 데이터 다운로드 및 SHA-256 검증 |
| [evaluate.py](evaluate.py) | 정답 데이터와 비교, 성능 지표와 오류 출력 |
| [tests/test_regression.py](tests/test_regression.py) | 추출·감성·평가·CLI 회귀 테스트 |

기존 README의 상세 설명과 확장 절차는 [설계 노트](docs/design-notes.md)에 보존했다.

## 2. 설치 및 실행 방법

Python **3.10 이상**이 필요하다. 분석과 일반 테스트는 표준 라이브러리만 사용한다. 최초 데이터 다운로드에는 인터넷 연결이 필요하며, 준비 후에는 오프라인으로 분석할 수 있다.

```bash
git clone https://github.com/js910/rule-based-nlp.git
cd rule-based-nlp
python setup_data.py
python -X utf8 main.py --text "정말 좋지 않다. 전화 (02) 123-4567"
```

Conda 사용 시 `python setup_data.py` 전에 아래 명령으로 [environment.yml](environment.yml)의 환경을 준비한다. Python 3.10 이상이 이미 있으면 생략할 수 있다.

```bash
conda env create -f environment.yml
conda activate rule-based-nlp
```

### 기본 출력 예시

기본 형식은 사람이 읽을 수 있는 텍스트다. 다음은 위 명령의 실제 출력이다. 토큰은 정규식으로 나눈 어절·영숫자·문장부호이며, 형태소 분석 결과를 가정해 표시하지 않는다.

```text
=== 정보 추출 결과 ===
입력: 정말 좋지 않다. 전화 (02) 123-4567

추출 결과:
- 이메일: 없음
- 전화: 02-123-4567
- 날짜: 없음
- 금액: 없음
- URL: 없음

=== 감성 분석 과정 ===
문장: 정말 좋지 않다. 전화 (02) 123-4567
분석 모드: 사전 + 부정·강조 규칙
토큰화: ["정말", "좋지", "않다", ".", "전화", "02", "123", "4567"]

감성 표현별 계산:
1. 표현: 좋지 → 사전 키: 좋 (+2)
   부정: 1회 / 강조·약화 가중치: ×1.5
   계산: (+2) × (-1)^1 × 1.5 = -3

최종 점수: -3
최종 판정: 부정
```

### 옵션

```bash
# 다른 프로그램에서 사용할 기존 구조의 JSON 출력
python -X utf8 main.py --text "정말 좋지 않다" --format json

# 부정·강조 규칙을 끄고 사전만 사용한 결과 확인
python -X utf8 main.py --text "정말 좋지 않다" --baseline

# 합계 0점을 긍정으로 처리
python -X utf8 main.py --text "좋다. 나쁘다." --binary
```

`--format text`가 기본값이다. 기존에 `main.py`의 표준출력을 JSON으로 읽던 프로그램은 `--format json`을 추가해야 한다. JSON의 `information`·`sentiment` 구조와 분석 함수의 반환 형식은 유지한다. 금액은 JSON에서 `{"amount": 5000, "currency": "KRW"}`, 텍스트에서 `5000 KRW`로 표시한다.

### 평가 및 테스트 실행

```bash
# 정보 추출 전체 오류 + 감성 오류 최대 30건과 평가표
python -X utf8 evaluate.py --errors 30

# 0점 처리 정책을 바꾼 이진 평가
python -X utf8 evaluate.py --binary --errors 0

# 회귀 테스트
python -m unittest discover -s tests -v
```

평가 출력을 파일로 저장하려면 Bash에서는 `python -X utf8 evaluate.py --errors 30 > evaluation.txt`, PowerShell에서는 `python -X utf8 evaluate.py --errors 30 | Out-File -Encoding utf8 evaluation.txt`를 사용한다.

[GitHub Actions](.github/workflows/tests.yml)는 push·PR·수동 실행 시 테스트와 커버리지 측정을 수행한다. 성공한 실행의 Summary에 커버리지 표가 표시되고, Artifacts의 `coverage-report`에 `coverage.txt`·`coverage.xml`이 보관된다. 커버리지는 테스트가 실행한 코드의 범위이며 분석 정확도와 다르다.

KNU 원본의 `word`·`word_root`·`polarity`를 읽고, 극성이 0이 아닌 지원 형식의 항목을 가공한다. 도메인 사전을 합친 최종 조회 키는 단어·어간 **7,891개**, 여러 어절 표현 **7,572개**다. 조회 키 수는 중복 제거·어간 가공 후의 수치이므로 원본 표제어 수와 다르다.

`extraction.jsonl`의 한 줄에는 입력 `text`와 정답 `expected`가 있다. 추출 함수에는 `text`만 전달하며, 정답은 결과가 나온 뒤 채점할 때 사용한다. 평가 데이터로 모델을 학습하지 않는다. NSMC는 원본 50,000건에서 본문이 빈 3건을 제외한 **49,997건**(긍정 25,171건·부정 24,826건)을 평가한다.

## 4. 규칙 설계

### 정규표현식과 정규화

Python 내장 `re`를 사용하며 각 패턴의 의도와 범위는 [extract.py](nlp/extract.py)에 주석으로 설명했다. 아래는 유형별 대표 변형과 반환 형식이다.

| 유형 | 지원하는 변형 예시 | 정규화 |
| --- | --- | --- |
| 이메일 | `user@example.com`, `a.b@sub.example.com`, `a+tag@example.org` | 도메인만 소문자로 변환 |
| 전화 | `(02) 123-4567`, `031 1234 5678`, `01012345678`, `+82 10-1234-5678`, `공일공-일이삼사-오육칠팔` | 국내 하이픈 형식 |
| 날짜 | `2024년 2월 29일`, `2024/2/29`, `2024-02-29`, `2024.2.29` | 달력 검증 후 `YYYY-MM-DD` |
| 금액 | `10,000원`, `1억 2천만원`, `$100`, `₩2,500` | 정수 금액과 통화 코드 |
| URL | `http://example.com`, `https://example.com/a?q=1`, `www.example.com` | 스킴·호스트 소문자화, `www.`에 `https://` 추가 |

`[0-9]{3,4}`는 자릿수 제한, `(?:...)`는 비캡처 그룹, `(?P<year>...)`는 이름 있는 캡처다. 날짜의 `(?P=sep)`는 같은 구분자 사용을 요구한다. 전후방 검사는 긴 숫자의 일부를 잘못 잡는 일을 줄인다.

탐지 우선순위는 URL → 이메일 → 전화 → 날짜 → 금액이다. 이미 찾은 범위와 겹치는 매칭은 제외하므로 URL 속 날짜를 별도 정보로 중복 추출하지 않는다. `2023-02-29`처럼 실제로 없는 날짜나 `10,00원`처럼 잘못된 쉼표 표기는 제외한다. 유형별 결과는 등장 순서대로 배열에 담으며, 같은 값의 반복은 유지한다.

### 감성사전과 토큰화

`load_lexicon()`은 KNU 사전을 가공한 뒤 도메인 CSV를 합친다. 정확히 같은 키는 나중에 읽은 도메인 점수로 덮어쓴다. 입력 문장은 `analyze()`에서 토큰으로 나누고, 여러 어절 표현을 먼저 대조한다. 같은 위치에서는 긴 표현을 우선하며 포함된 토큰을 다시 세지 않는다. 나머지는 `lookup()`에서 가장 긴 감성 어간과 허용 어미를 찾는다. `고마워 → 고맙` 같은 대응표는 일부 불규칙·비표준 형태를 보완한다.

### 부정·강조 규칙과 점수

```text
표현 점수 = 기본 사전 점수 × (-1)^부정 횟수 × 강조 가중치
문장 점수 = 찾은 표현 점수의 합
```

| 규칙 | 조건·처리 | 예시 |
| --- | --- | --- |
| 앞 부정 | 바로 앞 `안`·`못`으로 부호 반전 | `안 좋다` → -2 |
| 뒤 부정 | `-지` 계열 어미 뒤 `않다`·`못하다` 계열 표현 | `좋지 않다` → -2 |
| 이중부정 | `-지 않지 않다`와 지원 활용형 | `좋지는 않지는 않아요` → +2 |
| 일반 강조 | 매우·정말·아주·너무·무척·진짜 → ×1.5 | `정말 좋다` → +3 |
| 강한 강조 | 완전·엄청·굉장히 → ×2 | `완전 좋다` → +4 |
| 약화 | 조금·약간 → ×0.5 | `조금 좋다` → +1 |

가중치는 사람이 정한 값이다. 가장 가까운 강조어 하나만 적용하며, 바로 앞이 `안`·`못`이면 한 어절을 건너뛴다. 따라서 `완전 정말 좋다`는 +3, `정말 안 좋다`는 -3이다. `좋지, 않다`는 쉼표로 범위가 끊겨 부정이 연결되지 않는다.

양수는 긍정, 음수는 부정, 0은 기본적으로 중립이다. 0점은 감성 표현을 못 찾았거나 긍정·부정 점수가 상쇄된 경우이며 텍스트 보고서에 사유를 표시한다. `--binary`에서는 두 경우 모두 긍정으로 처리한다. 점수는 확률이 아니며 문장 길이에 따라 합계 범위가 달라진다.

`--baseline`은 `use_rules=False`로 실행해 부정 반전·강조 배수만 끈다. 사전·토큰화·활용형 조회는 동일하다. `정말 좋지 않다`는 사전만 사용하면 +2, 규칙을 적용하면 -3이다. 이 비교로 규칙의 효과를 측정한다.

## 5. 평가 결과

아래 값은 동일한 고정 데이터에서 `evaluate.py`의 기본 모드와 이진 모드를 재실행해 확인한 결과다.

### 정보 추출

직접 작성한 60문장에서 정규화된 값의 출현 횟수를 비교한다. 같은 값이 반복되면 반복 횟수도 비교한다. TP는 맞게 추출한 값, FP는 잘못 추가한 값, FN은 빠뜨린 값이다.

```text
Precision = TP / (TP + FP)
Recall = TP / (TP + FN)
```

| 유형 | TP | FP | FN | Precision | Recall |
| --- | ---: | ---: | ---: | ---: | ---: |
| 이메일 | 10 | 0 | 2 | 100.0% | 83.3% |
| 전화 | 10 | 0 | 1 | 100.0% | 90.9% |
| 날짜 | 9 | 0 | 2 | 100.0% | 81.8% |
| 금액 | 9 | 0 | 2 | 100.0% | 81.8% |
| URL | 9 | 1 | 2 | 90.0% | 81.8% |

이 결과는 직접 만든 소규모 표본의 성능이다. 실제 고객 문의 전반에서 정밀도가 100%라는 의미는 아니다. 오류가 발생한 문장·유형 조합은 9건이며, 값 단위 FP·FN의 합과는 다르다.

### 감성 분석: 규칙 적용 전후

기본 모드는 0점을 중립으로 예측한다. NSMC 정답은 긍정·부정뿐이므로 중립 예측은 오답으로 집계한다.

| 설정 | 정답 수 / 전체 | Accuracy | 긍정 F1 | 부정 F1 | Macro F1 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 사전만 | 19,492 / 49,997 | 39.0% | 0.557 | 0.460 | 0.509 |
| 사전 + 부정·강조 규칙 | 19,725 / 49,997 | 39.5% | 0.562 | 0.464 | 0.513 |

Accuracy는 전체 문장 중 라벨이 맞은 비율이다. 클래스별 F1은 `2TP / (2TP + FP + FN)`, Macro F1은 긍정·부정 F1의 산술평균이다. 규칙 적용으로 정답이 233건 늘고 정확도는 약 0.5%p 개선됐다.

0점을 긍정으로 처리하는 `--binary` 조건도 별도로 비교했다.

| 이진 설정 | 정답 수 / 전체 | Accuracy | Macro F1 |
| --- | ---: | ---: | ---: |
| 전부 긍정 예측 기준선 | 25,171 / 49,997 | 50.3% | 0.335 |
| 사전만 | 30,458 / 49,997 | 60.9% | 0.577 |
| 사전 + 규칙 | 30,591 / 49,997 | 61.2% | 0.580 |

기본 모드와 이진 모드는 0점 처리 정책이 다르다. **39.5% → 61.2%를 규칙 추가의 효과로 해석하면 안 된다.** 규칙 적용 효과는 같은 표 안에서 비교한다. 사전·규칙 개선에 오류를 확인했던 NSMC 테스트셋을 재사용했으므로, 별도 데이터에 대한 일반화 성능은 확인하지 않았다.

## 6. 성공·실패 사례 분석

### 성공 사례

| 입력 | 결과 | 성공 이유 |
| --- | --- | --- |
| `+82 10-1234-5678` | `010-1234-5678` | 국가번호를 국내 형식으로 정규화 |
| `2024년 2월 29일` | `2024-02-29` | 날짜 패턴과 윤일 검증 |
| `1억 2천만원` | `120000000 KRW` | 원화 단위를 정수로 계산 |
| `https://example.com/2024-01-01` | URL만 추출, 날짜는 빈 배열 | 겹치는 범위의 중복 추출 방지 |
| `정말 좋지 않다` | -3, 부정 | 사전 점수 +2에 부정·강조 적용 |
| `좋지 않지 않다` | +2, 긍정 | 지원하는 이중부정 패턴 처리 |

## 7. 개선 아이디어 및 한계 분석

1. **표기가 명확한 실패부터 보완한다.** 대표전화, 통화 코드, 유로 기호는 정상·실패 예시를 함께 추가해 검증한다.
2. **규칙을 넓힐 때 오탐도 확인한다.** 구분자 없는 8자리 숫자를 모두 날짜로 처리하면 주문번호를 날짜로 오인할 수 있다. 누락 감소와 오탐 증가를 함께 비교해야 한다.
3. **띄어쓰기·활용형을 개선한다.** 현재는 정규식 토큰화와 수동 활용 규칙을 사용한다. 형태소 분석기 도입 여부는 같은 조건의 별도 검증 데이터에서 비교한다.
4. **복합 감성과 반어는 별도 과제로 다룬다.** 현재는 모든 표현을 합산하므로 `좋다. 나쁘다.`는 0점이다. 음식·가격처럼 대상별 감성은 분리하지 않고, 먼 부정·반어·조건절도 일반적으로 해석하지 못한다.
5. **도메인별 사전과 새 평가셋을 관리한다.** 단어를 추가하거나 규칙을 수정하면 기존 정상·실패 사례와 전체 평가를 다시 실행한다. 이미 검토한 테스트셋과 독립된 데이터로 일반화 성능을 확인해야 한다.

규칙 기반은 이메일·전화처럼 형식이 일정하거나 판정 근거가 중요한 작업에 적합하다. TF-IDF와 코사인 유사도는 문서를 벡터화해 유사 문서를 찾는 데 적합하며, 레이블이 충분하면 TF-IDF 기반 분류기와 감성 분석 성능을 비교할 수 있다. **이 저장소에는 TF-IDF 비교 실험, 개인정보 마스킹, 대상별 감성 분석은 구현하지 않았다.**
